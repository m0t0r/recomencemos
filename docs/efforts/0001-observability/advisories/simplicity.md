## The simplest thing that satisfies the intent

Two workspaces, but thinner ones:

- `@repo/errors` — an `AppError` class with **five** fields (`code`, `status`, `message`, `userMessage`, `requestId`), `isAppError` on a registered symbol, `toErrorResponse` building the body field-by-field. No `defineErrors`, no error sets, no `scope`/`reason`/`hint`, no `attributes`-vs-`metadata` split.
- `@repo/observability` — one pino singleton from a pure `createLoggerOptions(env)`, always JSON, one redaction list, one pure `scrubEvent`, one `reportError`.
- In `apps/web` — `instrumentation.ts` (DSN check, then `onRequestError`), `sentry.server.config.ts`, `instrumentation-client.ts`, `error.tsx` + `global-error.tsx` with the digest guard.
- The `no-console` rule, `turbo.json` env, the ADR, the policy keys, the runbook, the README rows.

**What that breaks, checked against your own numbers:** nothing. I walked NFR1–NFR14 against this reduction and every one still holds. NFR4 is the only place where a draft decision earns its keep, and it does — a separate zero-dependency package makes `import pino` inside `@repo/errors` fail to *resolve* under pnpm's isolated store, whereas a subpath in one package would only fail the `.next/static` grep. That is a compile-time failure bought for one `package.json` and one tsconfig. **Concede it; the spec already names the alternative it beat, which is exactly right.**

## Recommend

- **Cut `defineErrors` and the "Error set" core entity.** No NFR binds it, no story names it, and after the draft's own `Out of Scope → shipped example route handlers`, it has **zero** call sites in the repo — its only exercise is a test written for it. It is a guess about a downstream project's error vocabulary, made in a template that explicitly refuses to ship an error taxonomy two sentences earlier ("No taxonomy ships — `code` stays a free string"). Stories 3 and 4 survive intact without it. Adding it later is additive: a new export over an unchanged class, no migration.
- **Collapse `attributes`/`metadata` to one `context` field, and drop `scope`/`reason`/`hint`.** `AppError` currently carries ten fields to satisfy a wire projection of three (`code`, `userMessage`, `requestId`) plus one operator `message`. The `attributes`/`metadata` split reads as a nod to Q4's "redaction cannot reach inside a nested object" — but the draft never states that consequence, and if that *is* the reason, it belongs as one sentence in `CLAUDE.md` rather than as two fields a caller must choose between. Two fields with no stated rule for picking one is a coin flip every future reader pays for.
- **Cut story 14 and `app/not-found.tsx`.** The bundled Next 16 docs are explicit: `onRequestError` fires when "the Next.js server captures the error" — a `notFound()` is a routing outcome, not a server error, so **the 404 clause of NFR3 is already true with zero code written.** The draft ships a file whose stated job is to carry a comment "so nobody adds it later". A file that exists to assert an absence is the purest form of the thing this lens is for; one line in the runbook does the same work, and shipping `not-found.tsx` also drags NFR11 (WCAG 2.2 AA) onto a surface nobody asked for.
- **Delete NFR12's `beforeSend` status filter.** The Solution section already claims the routing rule — "thrown is reported, returned is logged" — *is* the quota lever. If that rule holds, the filter has nothing to drop; if it does not hold, the filter silently swallows the evidence. Worse, it drops a *thrown* `AppError` carrying a 4xx status — the auth bug producing 3,000 401s is exactly the incident you want to see. Two mechanisms for one guarantee, and the second one hides failures of the first.
- **Make `redactPaths` and `isReportingEnabled` module-internal.** The draft's own "Who may call it" column says `redactPaths` is for "the logger and the scrubber only" — both inside `@repo/observability` — and `isReportingEnabled` for "`instrumentation.ts`; the runbook", but a runbook is prose and `register()` already performs the DSN check itself (Story 7). NFR10's parity is proved by running both consumers over one input, not by exporting the list. Every public export is a shape a downstream project can depend on and you can no longer change.
- **Say whether the tunnel route ships.** It appears exactly once, in a list, with no story, no NFR, and no rationale. A tunnel is an unauthenticated POST proxy in `apps/web` that forwards arbitrary envelopes — structurally the same surface the Out of Scope section rejects in its first bullet ("a custom ingest endpoint is an unauthenticated write surface needing rate limiting, body caps, origin checks, and a schema"). Either move it to Out of Scope or state why the ad-blocker workaround is worth the surface the spec just refused.

## Risks

- **`pino-pretty` costs 14 transitive packages for a default nobody in this repo reads.** Measured: `pino@10` alone resolves to 14 packages; `pino@10 + pino-pretty@13` resolves to 28. This repo already chose happy-dom over jsdom on that exact axis (10 vs 39, recorded in `CLAUDE.md`), and `PRODUCT.md` names Claude Code as the second reader — the intent's own Q2 answer concedes the pretty stream "an agent cannot parse". The template therefore installs 14 packages to produce a format its documented primary consumer must switch off. The `LOG_FORMAT` option is also a textbook second code path: NFR9 pins the `json` branch to a hard assertion, and nothing pins the `pretty` branch at all, so it is under-tested from day one.
- **`@sentry/nextjs@10.70.0` resolves to 255 packages**, including `rollup@^4` and `@rollup/plugin-commonjs`. Q1 bought this and I am not reopening it — but the draft does not price it, and it should, because it is the largest single thing this effort adds to a downstream `pnpm install`. NFR6's engines check is correct as written (`@sentry/nextjs` declares `>=18`; `pino` and `pino-pretty` declare none — verified independently), so the `engineStrict` constraint is genuinely clear.
- **The prior spec on `feat/observability` found a cost this draft has dropped**: pnpm needs public hoist patterns for the two module-interception packages the Sentry SDK relies on (`import-in-the-middle` / `require-in-the-middle`). That is an edit to `pnpm-workspace.yaml` — a file `CLAUDE.md` says pnpm owns and oxfmt ignores. It will surface at Build as a surprise unless a deep dive names it.
- **Twelve `Must` stories.** Not a smell by itself, but stories 3 and 4 are marked "demoable on its own" and, with example route handlers Out of Scope, neither has a runtime demo. That claim should either be retracted for those two or the cut reversed.

## Could be cut

- **Story 14** (404 produces no report, no log line) → **Out of Scope**, because Next already guarantees it. Removes `app/not-found.tsx` and one clause of NFR3, and leaves a coherent shippable thing.
- **Story 13** is the only `Should` and it is not really optional — `CLAUDE.md` makes the README placeholder table a repo constraint. Consider promoting it to `Must` so the priority reflects reality; a `Should` nobody may skip is mislabelled.
- Nothing else in the `Must` list is cuttable without breaking a number. Stories 1, 3, 5, 7, 10 are the spine; 8, 11, 12 are documents with no moving parts; 6 and 9 each carry an NFR. That is a healthy result and worth saying so in Further Notes.

## Concerns

- [ ] **C-S1** — `LOG_FORMAT` defaults to `pretty` in development, keeping `pino-pretty` (+14 packages) and a second, unasserted code path. The inversion — always JSON, `pnpm dev | npx pino-pretty` as the documented human path — drops the dependency, drops the option, and makes NFR9 vacuously true. It also dissolves the destination-vs-transport worker question structurally rather than by argument. **This contradicts an approved answer** (intent Q2), so it is not mine to take. Note that `apps/web/next.config.ts` sets `logging.browserToTerminal: true`, so the dev stream is mixed-format under *either* default and any agent parsing it must already tolerate non-JSON lines — which weakens Q2's stated reason for pretty-by-default. **Risk if wrong:** if the intent's answer is kept, the template ships 14 packages and a permanently under-tested branch to serve a reader who must disable it. If inverted, `pnpm dev` is unreadable to a human without a pipe. **Owner:** Tech lead (reopening intent Q2 with the On-call lead).
- [ ] **C-S2** — Whether the template ships any call site for `@repo/errors`. `Out of Scope → Shipped example route handlers` means `AppError`, `toErrorResponse`, and the redaction list have zero production callers on the first commit; the boundaries receive a React error with a `digest`, not an `AppError`. **Risk if wrong:** the template's headline deliverable is a library with no user, `/implement` can tick stories 3, 4, and 9 only with unit-test evidence, and the first downstream developer discovers the intended usage from a test file. **Owner:** Tech lead.
- [ ] **C-S3** — NFR3 (exactly 1 event), NFR5 (100% trace-id equality), and NFR2 (exactly 1 startup line) have no evidence path. `## Testing Decisions` names three pure seams and says "No mocks"; none of the three can observe a Sentry event or a span. **Risk if wrong:** the three headline guarantees of this spec are verified once, by hand, by whoever has a Sentry account, and regress silently thereafter. **Owner:** Tech lead (with On-call lead).
- [ ] **C-S4** — Where the two new workspaces' tests run. `CLAUDE.md` states Vitest "is wired in `packages/design-system` only"; this effort makes it three. The prior spec answered this (a `test: vitest run` script per package, **no** runner config file, Node default environment) — reuse that rather than re-deciding, but the draft currently says nothing and `turbo run test` will silently cover nothing. **Risk if wrong:** two packages with test files and no runner, green by absence. **Owner:** Tech lead.

## Handoffs

- **Cutting `app/not-found.tsx` moves the guarantee from a file to framework behaviour.** That is a real move, not a free one: the claim becomes true by Next's design rather than by this repo's code, so it belongs in the runbook next to the quota notes, and it becomes false the day a downstream route handler throws its own not-found instead of calling `notFound()`. Name that condition where you name the cut.
- **Cutting `defineErrors` hands the error-vocabulary question to the first downstream project**, which is the correct edge — but only if the ADR (story 11) says so explicitly. Otherwise the next spec re-derives it from scratch, which is exactly the loop `docs/policy/` exists to close.
- **Removing the `beforeSend` status filter hands quota control entirely to the `thrown/returned` rule.** If any code path in `apps/web` throws where it should return, the quota lever is gone with no backstop. That is a Build-time discipline, and it should appear as an acceptance criterion on story 5 rather than as a second runtime mechanism.
- **Narrowing `@repo/observability`'s exports hands nothing to another edge** — but it does mean the redaction-parity test must exercise the logger and the scrubber over one input rather than asserting against an exported constant. Cheaper, and it tests the property NFR10 actually states.
