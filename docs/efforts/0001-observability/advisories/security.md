# Security advisory — 0001-observability

Read against `/Users/m0t0r/Developer/ai-native-project/docs/efforts/0001-observability/spec.md`, its `intent.md`, `docs/policy/security.md`, `docs/policy/data.md`, `docs/policy/operability.md`, and the code the spec lands on (`apps/web/next.config.ts`, `turbo.json`, `.oxlintrc.json`, `apps/web/package.json`).

The draft's core posture is good and unusually well-shaped for security: whitelist construction over deny-list, a zero-dependency isomorphic package as a *physical* client-safety guarantee rather than a convention, `userMessage` defaulting to a constant instead of `message`, replay and user-feedback excluded, 404s silent. What follows is what that shape does not yet cover.

## Recommend

- **Name the trust boundaries explicitly; there are seven and the spec walks none of them.** This change is almost entirely boundary work, and the draft reads as a component design. The seven: (1) attacker-controlled request headers/query → `onRequestError` → both sinks; (2) app server → Sentry ingest (a **third-party processor** receiving error content, URLs, and headers); (3) app server → stdout → an unnamed drain; (4) build machine → Sentry, holding a write-scoped token; (5) browser → Sentry ingest via a **public** DSN; (6) browser → the tunnel route, if it ships; (7) `AppError` → RSC payload / Server Action return value → browser. Boundary 7 is the one the design's own whitelist does not cover, and boundary 6 is the one the intent explicitly refused elsewhere.

- **`toErrorResponse` guards one wire, and Next has two.** Story 4 and the whitelist protect the Route Handler path — a `{ status, body, headers }` value the handler turns into a `Response`. **A Server Action does not return a Response.** Its return value is serialized straight into the RSC payload, as is any `AppError` passed as a prop to a Client Component. On both of those paths there is no `toErrorResponse`, no whitelist, and `AppError.toJSON()` — which the contract says returns a deterministic object omitting only `cause` — publishes `message`, `reason`, `hint`, `attributes`, and `metadata` to the browser. The design's headline claim ("adding a field to the type cannot leak it") is true of one egress and false of the other two. Settle it: either `@repo/errors` exports the Server-Action-shaped projection too (same whitelist, different envelope), or the spec states that an `AppError` never crosses the server/client line as a value and says what enforces that.

- **Put the redaction list and `scrubEvent` in `@repo/errors`, not `@repo/observability`.** As drafted this is a contradiction the spec cannot satisfy: NFR10 demands redaction parity between the log line and the reported event; the redaction list has "exactly two consumers"; and the client is a **third** reporting site (`lib/report-client-error.ts`, `instrumentation-client.ts`) which the spec forbids from importing `@repo/observability`. So the browser SDK ships with no scrubber at all, and the one list that "cannot disagree" disagrees with the client path by construction. `scrubEvent` is specified as pure with no SDK call, and `redactPaths` is a `readonly string[]` — both are zero-dependency and belong in the isomorphic package. Type the event structurally rather than importing Sentry's `ErrorEvent`, so `@repo/errors` keeps its zero-dependency guarantee.

- **`scrubEvent` covers `ErrorEvent`, and NFR12 keeps transactions on.** A trace sample rate of ≤0.1 means Sentry sends **transaction** events too, carrying URLs (with query strings), span attributes, and breadcrumbs — a separate egress with a separate hook (`beforeSendTransaction`, `beforeBreadcrumb`). One pure scrubber typed to `ErrorEvent` and wired to "the pre-send hook" (singular, in the contract table) leaves those unscrubbed. Decide whether the scrubber is polymorphic over every egress hook, or whether transactions are off by default for a template.

- **State `sendDefaultPii: false` in the spec rather than inheriting a vendor default, and scrub before send rather than at the vendor.** `onRequestError`'s `request` parameter is documented in the bundled Next 16 docs as `{ path, method, headers }` where `path` is "resource path, e.g. `/blog?name=foo`" — the query string included — and `headers` is the full inbound header map. `Sentry.captureRequestError` is handed that object. Sentry does perform server-side data scrubbing, but server-side means **the raw `authorization` header and any query-string token crossed the boundary before being scrubbed**. For a template whose whole thesis is "the two paths cannot disagree," relying on vendor-side scrubbing is a different trust posture and should be a stated decision, not a default.

- **Say where `requestId` comes from.** It appears in the `AppError` entity, on the wire body, and as the user-visible reference in Story 6, and the spec never says whether it is generated server-side or read from an inbound header. If it is inbound (`x-request-id` is the obvious choice), it is attacker-controlled text flowing unvalidated into every log line and onto the wire. pino's JSON encoder escapes it, so `LOG_FORMAT=json` holds — but the **pretty** stream is the dev default per NFR9/Story 2, and it is what `next-dev-loop` and `browserToTerminal: true` put an agent in front of. That is log-forging and prompt-injection surface aimed at the repo's second reader. Generate it server-side, or accept an inbound value only after a shape and length check at the boundary, once.

- **`isAppError` checks a registered symbol, and `Symbol.for()` is a shared global registry.** The rationale (surviving Next's separate server/client realms) is correct and I would keep the mechanism. But any object can set `obj[Symbol.for("...")] = true`, so `isAppError` is a *claim*, not an identity proof. The consequence is concrete on the `toErrorResponse` boundary: a forged object that passes the check gets its `status`, `code`, and `userMessage` reflected onto the wire, letting a caller choose the response status and the user-visible string. Cheap fix, and it belongs in the contract: the whitelist construction validates the **type and length** of each field it copies, and never trusts `status` to be a number in range.

- **Give the audience split an NFR with a number.** It is the most important security property in this spec and it is the only one with no measurable requirement. NFR3 counts events and lines; NFR4 counts bytes of pino in the client bundle; NFR10 covers redaction parity. Nothing asserts that operator prose stays off the wire. The countable form is available and Testing Decisions seam 1 already reaches it: for an `AppError` whose `message`, `reason`, `hint`, `attributes`, and `metadata` each carry a distinct sentinel string, the serialized wire body contains **0** occurrences of any of them, and exactly three keys. Without that `Binds:` line, `/to-tickets` cuts Story 4 with no acceptance criterion for the property Story 4 exists to provide.

- **Decide the tunnel route in or out, and if in, bound it.** It is currently listed casually under "stays Sentry-specific, deliberately" alongside source-map upload. A tunnel route is not framework integration — it is a **new unauthenticated inbound POST endpoint in your app that relays arbitrary bodies to a third party**. The intent's Out of Scope refuses a browser-side log sink in exactly these words: "an unauthenticated write surface needing rate limiting, body caps, origin checks, and a schema — decisions this template must not make on a downstream project's behalf." The same sentence applies verbatim to the tunnel. If it ships it needs DSN-host and project-id validation, a body cap, and a rate limit; my recommendation is that it does not ship and the spec says why, since a template with no CSP has nothing to tunnel around.

- **State the source-map disposition.** `withSentryConfig()` generates client source maps to upload them. Whether they are deleted from `.next/static/` after upload is a one-line configuration decision with a direct disclosure consequence — left behind, the app's full client source is served publicly. It also decides who at the org can read the source via Sentry.

- **`reportError` must not be able to suppress the log line.** Story 5 orders the calls report-first-then-log, and the reasoning (the span is still resolvable) is right. But a thrown SDK error, a network failure, or a quota rejection in `reportError` then means the incident appears in **neither** sink — the failure mode that only shows up during the outage you needed it for. Keep the ordering; state that the report call cannot propagate. Same question for `scrubEvent`: if it throws on a malformed event, the design must fail **closed** (drop the event) rather than sending it unscrubbed, and that is a design decision, not an implementation detail.

- **Write the `metadata` rule.** The intent's Q4 lists "the wording of the metadata rule in `CLAUDE.md`" among what it blocks, and the draft does not carry it. It matters more than the list does: `metadata` is specified as "nested arbitrary," and a fixed path list cannot reach into arbitrary nesting, so `metadata` is the designed-in bypass around both consumers of `redactPaths`. `docs/policy/data.md` already supplies the vocabulary — `secret` is never logged, `personal` carries a retention period — so the rule has a settled basis: never place a value into `metadata` you have not classified.

- **Scope `SENTRY_AUTH_TOKEN` to the task that needs it.** The table puts it in `globalPassThroughEnv`, which hands a write-scoped token to **every task in every workspace** — `dev`, `lint`, `test`, `check-types`. Turborepo supports task-level `passThroughEnv`; least privilege says it reaches `apps/web`'s `build` and nothing else. Separately, the stated rationale ("never hashed, so rotation does not bust every build") does not survive contact with `turbo.json`, where `build` declares `"inputs": ["$TURBO_DEFAULT$", ".env*"]`. A developer putting the token in `.env.local` — the obvious place, and there is no `.env.example` in the repo to steer them elsewhere — has its content hashed into the build key regardless of the env declaration. The spec should say the token lives outside `.env*` and where instead, and the README placeholder row should say it too.

## Risks

- **Redaction parity is stated as an NFR and is unachievable as designed.** NFR10 binds Story 9. The client report path cannot import the list. As written, Build either discovers this and improvises a second list — the exact divergence the "one list, two consumers" entity exists to prevent — or ships a client SDK with no scrubbing and ticks NFR10 against the server path alone.

- **`console.error` is a third diagnostic path with no redaction whatsoever.** Q5's allow-list is settled and I am not reopening it, but the security consequence should be named where the spec makes its "the two paths cannot disagree" claim. `console.error(err)` on the server writes an unredacted, unstructured, uncorrelated line to the same stdout the drain reads — bypassing `redactPaths` entirely. In a client boundary it writes the operator `message`, `reason`, and `metadata` into the user's console, defeating the audience split the type exists to enforce. The intent's own mitigation ("the boundaries reach for `AppError` rather than `console.error`") is a convention with no NFR and no lint rule behind it.

- **The public DSN is the unauthenticated write surface the intent refused.** `NEXT_PUBLIC_SENTRY_DSN` is public by construction — that is how Sentry works and is not a flaw. But it means anyone can POST events into the project's quota, and Q3 established that the free tier **drops data rather than billing** at the cap. So a trivially cheap attack blinds the monitoring during the incident it causes. The intent rejected a custom ingest endpoint for being unauthenticated; the design ships the same property operated by a vendor and does not say so. NFR12 caps the *trace* sample rate and says nothing about error event volume. The mitigations exist Sentry-side (spike protection, inbound filters, allowed domains) and belong in the Story 8 runbook, not left implicit.

- **Cache Components is on, and the "returned is logged" rule collides with it.** `docs/policy/data.md` records as settled-by-the-stack that `use cache` and `use cache: remote` are shared across all users. A **thrown** `AppError` is not cached — fine. A **returned** one, which is the branch the design routes through `toErrorResponse`, is an ordinary return value: returned from inside a `use cache` scope, the error body and its `requestId` become a shared cache entry served to every subsequent user. The spec says nothing about whether an `AppError` may cross a `use cache` boundary. Adjacent and smaller: a log line emitted inside a cached function is emitted only on a miss, so its `trace_id` mixin correlates to the **populating** request's span — which makes NFR5's "100% of log lines inside a request carry `trace_id` equal to the event's" false for cached scopes, in a way that quietly mis-correlates one user's incident to another user's trace.

- **Choosing Sentry ships a data processor and a de facto retention while `log-retention` stays `UNSET`.** Q4's reasoning for leaving the retention keys unset is sound *for stdout*, where the template has no drain. It does not hold for the reporting path: the vendor is now settled, so error events — which carry request paths, headers, and whatever is in `attributes` — are retained on Sentry's schedule, in Sentry's regions, by a sub-processor a downstream project in a regulated regime inherits without being told. The template does not have to solve this; it has to say it in the Story 8 runbook so the first regulated adopter finds it before their first audit rather than after.

- **NFR3's report-once property has no automated regression guard.** The digest guard in `app/error.tsx`, the `onRequestError` single-site rule, and the `not-found.tsx` silence all live in `apps/web`, which has no `test` script by deliberate policy and verifies through `next-dev-loop`. Report-once is not only a quota lever — it is the control that bounds the blinding attack above. A future edit to a boundary re-enabling unconditional reporting (which is, note, what Sentry's own documented example does) turns it red with nothing failing.

- **`NEXT_PUBLIC_RELEASE` publishes the release identifier to every browser.** Correct and normal for Sentry, but it is a "what crosses to the client is published" item and the spec's env table does not mark it as such. It should carry one line saying the value must be a version or SHA and nothing else, because it is a `NEXT_PUBLIC_*` placeholder a downstream project fills in.

## Concerns

- [ ] **Where `SENTRY_AUTH_TOKEN` lives, what scope it carries (org-wide vs project-scoped, `project:releases` only), and who rotates it.** **Risk if wrong:** a write-scoped token in `.env.local` — hashed into the build cache by `turbo.json`'s `.env*` input, and passed to every task by `globalPassThroughEnv` — leaks and lets a third party write releases and artifacts across the org's Sentry projects. **Owner:** Security owner. **Unblocks by setting:** `docs/policy/security.md` → `secret-store`

- [ ] **Whether the app ships a CSP, and therefore whether the Sentry tunnel route has a reason to exist.** **Risk if wrong:** the tunnel ships as an unauthenticated same-origin POST relay solving a problem the template does not have, or the browser SDK is silently blocked by a CSP added later and client errors stop arriving with no signal. **Owner:** Security owner. **Unblocks by setting:** `docs/policy/security.md` → `csp-policy`

- [ ] **What may lawfully cross to Sentry — IP address, user agent, request headers, request path with query — and for how long it is retained there.** **Risk if wrong:** a template default that is a processor agreement and a retention decision a downstream project never made; also decides whether `sendDefaultPii: false` is sufficient or whether headers must be stripped before send. **Owner:** Security owner (with Data lead). **Unblocks by setting:** `docs/policy/security.md` → `compliance-regime`

- [ ] **Who the adversary is for a template with no auth.** **Risk if wrong:** the public-DSN quota-exhaustion path, the log-injection path through `requestId`, and the tunnel route are each either a real threat needing a mitigation in the Story 8 runbook or explicitly out of scope — and the spec cannot say which without this. **Owner:** Security owner. **Unblocks by setting:** `docs/policy/security.md` → `threat-model-scope`

- [ ] **What blocks a release when `@sentry/nextjs`, `pino`, or `pino-pretty` carries a CVE.** **Risk if wrong:** this is the first effort adding runtime dependencies beyond the framework, all three sit on the request path, and one of them ships in the client bundle — with no threshold there is no answer to "does this advisory stop the release." **Owner:** Security owner. **Unblocks by setting:** `docs/policy/security.md` → `dependency-policy`

- [ ] **Whether `AppError` values may cross a `use cache` boundary.** **Risk if wrong:** an error returned from inside a cached scope is stored and served to every user, publishing one request's `requestId` and any per-request `userMessage` to others; and log lines inside cached scopes carry the populating request's `trace_id`, breaking NFR5 silently. **Owner:** Tech lead (arbitration), with Data lead — this one is a concern under the data lens too and should not be answered twice.

- [ ] **Whether the scrubber fails closed.** **Risk if wrong:** a malformed event throws inside the pre-send hook and the SDK's behaviour on that throw — which varies by version — decides whether an unscrubbed event is transmitted. A vendor default is the wrong place for that decision. **Owner:** Security owner.

## Handoffs

- **Operability** — I am recommending an error-event rate cap and Sentry spike protection as the mitigation for the public-DSN blinding path, but the rate is a control band and I do not own the number. It needs a metric, a normal range, and an escalation, per `docs/policy/operability.md`. Note that `alert-destination` and `error-budget-policy` are both `UNSET`, so "what happens outside the band" currently has no answer.

- **Data** — the classification of a log line and of a reported event. `docs/policy/data.md` fixes the vocabulary and says a log line inherits the classification of what it contains, but nothing in the spec assigns a class to the `attributes` / `metadata` / `requestId` fields, and the `metadata` rule I am recommending needs that assignment to be writable as a rule rather than as advice. The `use cache` concern above is the same finding from two lenses and should be settled once.

- **Simplicity** — I have recommended moving `redactPaths` and `scrubEvent` into `@repo/errors`, and adding a second projection for the Server Action / RSC egress. Both add surface to the package whose selling point is that it has almost none. That is a real trade and I would rather it be arbitrated than have my version win by default.

- **UX** — Story 6's user-visible reference identifier. I need to know *which* identifier is shown (Sentry event id, `requestId`, or Next's `digest`) before I can say whether it discloses anything; the design differs materially between the three. NFR11's accessibility requirement at the root boundary is not mine.

## Not applicable

- **Authorization, sessions, roles, tenancy, IDOR.** This template ships no auth and no user model. There is no read path with an owner, so there is nothing to scope per-tenant and no ownership edge to check. `auth-provider`, `session-lifetime`, and `mfa-requirement` in `docs/policy/security.md` genuinely do not bind this change, and I am not raising them.

- **Data-at-rest, migrations, row-level access.** No database, no ORM, no `remote-cache-handler`. Every key in `docs/policy/data.md` is `UNSET` by necessity rather than by omission.

- **Server Action authorization and the "a page check does not protect its actions" rule.** This effort adds no Server Actions and no Route Handlers. If Design reverses the "no shipped example route handlers" exclusion under Out of Scope, that reverses this too — an example handler is an example of authorization as much as of error shape.

- **Session replay and user feedback**, which are the highest-PII Sentry integrations, are excluded by NFR12 and by the intent's Out of Scope. Checked, and the exclusion is the right call for a template.

- **CI secret handling.** There is no `.github/workflows/`, so the only place `SENTRY_AUTH_TOKEN` exists is a developer's machine. The concern above covers that; the pipeline half arrives with CI.

- **`pentest-cadence`.** No deployed surface to test.

## What I could not check

- **`@sentry/nextjs@10.70.0`'s actual behaviour is unverified.** Neither `@sentry/nextjs` nor `pino` is installed in this repo — I confirmed both are absent from `node_modules`. So NFR6's engines claim (`>=18`), the `sendDefaultPii` default, which hooks the SDK offers for transactions and breadcrumbs, and what it does when `beforeSend` throws are all recalled rather than read. Every one of those is load-bearing for a recommendation above, and each should be re-verified against the installed package at Build rather than trusted from this advisory.

- **Whether Sentry's server-side scrubbing covers the `authorization` header on the `captureRequestError` path** — I could not verify this without the package, and the recommendation to scrub before send stands regardless, since vendor-side scrubbing means the value already crossed.
