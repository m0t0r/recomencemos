# @repo/design-system

Guidance for working inside `packages/design-system`. Repo-wide conventions are in the root `CLAUDE.md`.

**`@repo/design-system` has no build step.** Its `exports` map points subpaths straight at source — `"./components/*": "./src/components/*.tsx"`, plus `./lib/*`, `./hooks/*`, `./globals.css`, and `./postcss.config` — so consumers import raw TSX (`import { Button } from "@repo/design-system/components/button"`) and Next.js transpiles it. There is no `build` script and no `dist` in the dependency graph. The file name _is_ the public subpath; there is no barrel file to update.

**The design system is shadcn/ui on Base UI, not Radix.** Components were generated from preset `b1Z6BvKBU` (`vega` style, `lucide` icons, Inter) with `--pointer`, which is why `globals.css` ends with a `@layer base` rule giving every non-disabled `button` / `[role="button"]` `cursor: pointer`. **The colour tokens are no longer that preset's** — they were chosen for this product with #178 (`DESIGN.md` → The world), so `components.json` reads `"baseColor": "neutral"` and the palette is a `--brand-*` ramp at hue 268. Re-applying a shadcn preset would overwrite them, and `apps/web/design-tokens.test.ts` would go red on the next `pnpm test`.

- **Add components with the CLI, never by hand:** `pnpm dlx shadcn@latest add <component> -c packages/design-system`. `packages/design-system/components.json` already maps the aliases to `@repo/design-system/*`, so generated imports come out correct.
- **Base UI, not Radix**, means custom triggers use the `render` prop, not `asChild` — `<DialogTrigger render={<Button>Open</Button>} />`.
- **Files under `src/components/` are registry output.** Prefer re-running the CLI (`add --diff` / `--overwrite`) over editing them, because hand edits are lost on the next update. That is also why the two a11y rules they trip are turned off through scoped `overrides` in `packages/design-system/.oxlintrc.json` rather than with inline `oxlint-disable` comments the CLI would clobber.
- The `toast` re-export at the bottom of `sonner.tsx` is **ours**, not registry output — keep it when regenerating. `sonner.tsx` also has its registry `useTheme()` call removed; the CLI will put it back on an overwrite.
- `sidebar.tsx` and `src/hooks/use-mobile.ts` also each trip one non-a11y rule the CLI's own output causes — `react/set-state-in-effect` on the media-query listener, `no-shadow` on the sidebar's own setter — and both are scoped in `.oxlintrc.json` for the same reason the a11y ones are: an inline disable would be clobbered by the next `add`.
- `button.tsx` carries one divergence, marked in the file and to be re-applied after an overwrite (#160). **The `cva` call lives in `button-variants.tsx` and `button.tsx` does not re-export it**, so `import { buttonVariants }` no longer drags `@base-ui/react/button` in with it — which it did for every client module styling a `<Link>` that must announce as a link. The re-export is deliberately absent rather than kept for compatibility: leaving it would make the old specifier go on working, and the split would be undone by the first import copied from an older file.
- `avatar.tsx` carries one divergence, marked in the file and to be re-applied after an overwrite (#220). **A fourth size, `xl` (64 px)**, for the one job the registry's three do not cover: a _portrait_, where the face is the subject, rather than a scanning anchor beside a row. It is a size on the component rather than a class at the call site because the ratios travel with it — the fallback initial steps to 20 px, and `AvatarBadge` and `AvatarGroupCount` step with the ring instead of staying drawn for a 40 px one.
- `input.tsx` carries one divergence, marked in the file and to be re-applied after an overwrite (#32). **The class string lives in `input-variants.tsx`** — the split `button-variants.tsx` made for Base UI's weight, made here for a different reason: there is one control this system has no component for, a `<select>` that works with JavaScript unavailable, and before the split the only way to give it the registry's box was to copy the string. The copy had already lost the `aria-invalid` ring and the disabled state, which is exactly the drift a second copy produces. `selectBox` there is that box plus `appearance-none` and the chevron the platform stops drawing once it is applied.
- `sidebar.tsx` carries two divergences, both marked in the file and both to be re-applied after an overwrite. **`Sidebar` takes `mobileTitle`/`mobileDescription` and `SidebarTrigger` takes `label`**, each defaulting to the registry's own English wording: the registry hard-codes three `sr-only` strings, this product's document is `lang="es-CO"`, and an English passage announced with Spanish phonemes is a WCAG 2.2 AA 3.1.2 failure. None of the three is reachable from outside — a dialog's accessible name comes from its title, and the trigger's is `sr-only` text rather than an attribute — so a prop was the only way to keep the copy in the app where [ADR-0012](../../docs/adr/0012-spanish-is-the-interface-english-is-the-code.md) puts it. **And every `cn` import in `sidebar.tsx`, `sheet.tsx`, `tooltip.tsx`, `table.tsx` and `kbd.tsx` was rewritten** from `from "cn"` to `from "@repo/design-system/lib/utils"`: the CLI resolved the `utils` alias to a **package on npm called `cn`**, added it to `package.json`, and emitted imports pointing at it. Check for that after any `add`, and drop the dependency if it reappears.

**What a registry component costs a route is decided in the app, not here** (#160). Three rules, and they are written down because the measurement that produced them cost a production build and a chunk-by-chunk read, and because every one of them is invisible in a diff.

- **A popup primitive goes behind a client-side `dynamic()`, and in a layout that is not optional.** `Menu`, `Select`, `Dialog` and `Popover` all pull floating-ui — the positioner, the focus guards and the scroll lock — and in a layout there is no route below that does not pay for it. The session menu is the worked case: it was in the first load of every route under `(site)` and `(admin)` for a menu behind an avatar a signed-out visitor never sees, and taking it off took `/` from **219 KB to 165 KB** gzip and `/publish` from **341 KB to 291 KB** (measured 2026-09-07; `pnpm build && pnpm page-weight`, which is the only way this figure may be quoted — re-take it rather than repeat it). `apps/web/app/_components/session-menu/session-menu-deferred.tsx` is the shape: a `"use client"` module holding the `dynamic()`, rendered where the component used to be.
  **Leave SSR on.** `ssr: false` measures identically and costs the markup a `<noscript>` fallback needs, so it buys the same bytes and loses a no-JavaScript path.
  **And do not reach for `next/dynamic` in the Server Component itself** — measured at 65.6 → 66.2 KB of Base UI, which is no effect at all. A route's client-reference manifest carries every client module reachable from the server graph whether the import is static or dynamic, so the deferral has to happen on the client side of the boundary. Next's own lazy-loading guide says so in one line: _"When a Server Component dynamically imports a Client Component, automatic code splitting is currently not supported."_ It is recorded here because it is an afternoon to rediscover.
- **`"use client"` is where the cost is decided, not the registry.** A registry component imported from a Server Component ships no JavaScript at all; the same component imported from a `"use client"` file ships Base UI's core, and a popup ships floating-ui with it. So the reviewable question is never "is this component heavy" — it is **which client components import which registry components**, and it is one grep: `grep -rl '"use client"' apps/web/app | xargs grep -l '@repo/design-system/components/'`.
- **Deep subpath imports are already correct** — `@base-ui/react/menu`, never the package root — so there is nothing to fix on that axis and `experimental.optimizePackageImports` buys nothing here. Do not add it.

**Tailwind v4, one stylesheet, owned by the design system.** `packages/design-system/src/styles/globals.css` holds the private `--brand-*` ramp, the semantic `:root` tokens, and the `@theme inline` map that is the only seam components reach through; `apps/web/app/layout.tsx` imports it as `@repo/design-system/globals.css` and `apps/web/postcss.config.mjs` re-exports the package's PostCSS config. There is no `tailwind.config.js` — v4 is CSS-first. The `@source` globs in that file are what tell Tailwind to scan `apps/**`, so a new app workspace needs a glob added there or its classes will be missing from the build. **There is no dark mode.** The paper is the product's one ground (`DESIGN.md` → The world), and `next-themes`, the provider and the toggle are gone — so there is no `.dark` block and no `dark` variant. Do not add `dark:` overrides; add the mode deliberately or not at all. Use semantic tokens (`bg-background`, `text-muted-foreground`) throughout.

**Contrast is a test, not a memory.** `apps/web/design-tokens.test.ts` resolves every semantic text pair in `globals.css` and fails under WCAG 2.2 AA's 4.5:1, and every non-text pair — `input`, `ring`, the five chart slots — under SC 1.4.11's 3:1. A change to an `L` value is red on the next `pnpm test` before it is reviewed; the tightest pairs today are `chart-5` on `background` at 3.04 and `input` on `background` at 3.85.

## Why the test DOM is happy-dom

**The DOM environment is happy-dom, not the jsdom Next's docs prescribe.** That is a deliberate deviation from the framework's documented path, so it was measured rather than preferred. Three axes, all favouring happy-dom:

|                           | jsdom 30                               | happy-dom 20          |
| ------------------------- | -------------------------------------- | --------------------- |
| `engines.node`            | `^22.22.2 \|\| ^24.15.0 \|\| >=26.0.0` | `>=20.0.0`            |
| transitive packages       | 39                                     | 10                    |
| vitest `environment` cost | ~330 ms per test file                  | ~135 ms per test file |

The engines line is the one that forced the decision: with `engineStrict` on, jsdom raises this repo's floor from any 24.x to 24.15+, which is a narrower runtime than anyone working here should have to hold for a test dependency. The environment cost is paid **per test file**, so it scales with the suite rather than being a one-off.

**The correctness axis went the other way from the folklore.** A probe of eighteen DOM APIs found nine differences and every one favoured happy-dom: `matchMedia`, `ResizeObserver`, `IntersectionObserver`, `scrollIntoView`, `dialog.showModal`, `inert`, `checkVisibility`, `elementFromPoint`, and `Range.getClientRects` are all missing or throwing under jsdom and present under happy-dom. Nothing was present under jsdom and missing under happy-dom. That matters concretely here: `next-themes` reads `matchMedia` and Base UI reaches for `ResizeObserver`, so the jsdom route needs a setup file full of mocks before the first component test runs.

Be honest about what that probe shows, though: it tested **presence, not fidelity**. jsdom's stated philosophy is to omit what it cannot implement correctly, so a happy-dom API that exists but never fires would be worse than an absent one you knowingly mocked. `src/components/dialog.test.tsx` is the guard against that — a portal plus a real `user-event` click is where a DOM environment actually breaks, and it is the case a real surface hits long before it hits Button. If it ever fails, reconsider the environment rather than the test.
